# 从仿真到实体：复用边界与接入指南

本文是[商业价值与产品设计](PRODUCT_DESIGN.md)的开发者延伸：购买前先了解玩法，开始开发后继续复用语音和动作软件，逐步接上实体 MicroDuck。代码核对基线为 `385a429`，更新于 2026-10-27。

**结论：上层语音与基础动作调度有复用基础，实体接入仍需要适配、感知反馈和实机校准。** 当前没有实体机器人验收，也没有统计可复用代码的百分比或节省的开发工时。本文描述现状并给出接入计划，不表示实机功能已经上线。

## 1. 为什么有复用基础

当前已有三条清楚区分的执行路径：

- 首页 `PreviewBackend`：官方外观加脚本动画，不计算物理接触。
- 物理场景 `MuJoCoBackend`：进程内运行 MuJoCo 和官方 ONNX 策略，负责接触、姿态和场景状态。
- `RobotdBackend`：通过本机 Unix socket 向官方 `robotd` 发 JSON-RPC 命令，目前只做过官方仿真联调。

[motion.py](../src/duckking/motion.py)里的 `Backend` 协议包含 `move`、`head`、`body_pose`、`stop`、`reset`、`snapshot`、`close`，`MotionController` 在其上处理动作校验、请求去重、取消和结果。语音端通过工具调用进入控制器，不直接操作仿真关节或实体舵机。

官方 `duck-sim` 也以真实控制守护进程为基础，在电机 I/O 边界接上 MuJoCo；官方控制接口采用 Unix socket JSON-RPC。这支持沿现有协议适配，而不是重新编写电机控制系统。[官方仿真说明](https://github.com/pollen-robotics/microduck/blob/main/docs/robot/simulation.md) · [官方架构](https://github.com/pollen-robotics/microduck#under-the-hood)

不过，基础接口并没有覆盖全部场景：当前控制器把坐站、踢球、搬运、前滚翻等 `SCENE_ACTIONS` 限定为 MuJoCo；工坊还直接访问 `backend.grasp`、`ball_observation()` 等仿真对象。**只改一个 socket 路径，不能让十三幕和全部工坊任务自动在实机上运行。**

## 2. 模块复用清单

| 模块与代码入口 | 可以沿用的部分 | 接实体时需要做的工作 |
|---|---|---|
| 灵矽会话：[voice.py](../src/duckking/voice.py)、[opus.py](../src/duckking/opus.py)、[mcp.py](../src/duckking/mcp.py) | 会话、音频编解码、MCP 工具分发、超时、打断、请求关联 | 适配音频设备入口，逐台绑定身份；只向云端公布本机确实可用的工具 |
| 本地优先：[hybrid_voice.py](../src/duckking/hybrid_voice.py)、[local_commands.py](../src/duckking/local_commands.py) | 整句匹配、有界动作计划、未命中时原录音转交一次 | 本地规则按实机能力收窄；离线推理先留在服务器，是否上板需测资源占用 |
| 基础动作：[motion.py](../src/duckking/motion.py)、[robotd.py](../src/duckking/robotd.py) | 动作结构、去重与取消机制；现有移动、头部、姿态、停止及遥测适配 | 核对固件协议、坐标与单位，校准速度和幅度；补充实机完成条件及能力声明 |
| 场景和工坊：[simulation.py](../src/duckking/simulation.py)、[studio.py](../src/duckking/studio.py)、[studio_tasks.py](../src/duckking/studio_tasks.py) | 用户任务、状态机、步骤替换、暂停和结果呈现的设计 | 把直接读取 MuJoCo 的部分拆成观察、姿态、夹持等接口；重新实现实机执行与验证 |
| 音频设备：[voice.js](../frontend/src/voice.js)、[audio-output.js](../frontend/src/audio-output.js) | 按住说话体验、音频格式与队列边界、停止旧回复的语义 | 浏览器实现不能直接充当板载驱动；增加实体麦克风采集和扬声器播放实现 |
| 体验统计：[experience.py](../src/duckking/experience.py)、[statistics.py](../src/duckking/statistics.py) | 阶段定义、持久化、均值与分位数计算 | 增加实机观测来源和维度；将命令受理、物理开始、播放入队、实际出声分开 |
| 多鸭：[rooms.py](../src/duckking/rooms.py)、演出调度 | 会话隔离、设备白名单和点名语义的设计 | 当前 robotd 路径只开放房间 1；实机多鸭还需设备映射、连接所有权、同步与离线处理 |

“可沿用”不等于无改动搬上开发板。浏览器 JavaScript、服务器 Python 与官方 Rust 守护进程有不同运行环境；每个部署位置都要核对依赖、内存、CPU、网络和版本。

## 3. 仿真鸭的麦克风和扬声器在哪里

在当前 DuckKing 中，**浏览器提供音频输入输出，MuJoCo 提供运动与接触**。并没有为每只虚拟鸭模拟独立的麦克风、扬声器、回声或空间声传播。

| 使用方式 | 输入 | 输出 | 是否依赖灵矽 |
|---|---|---|---|
| 本地优先，整句动作命中 | 浏览器麦克风 → 服务器离线识别 | 动作、文字和本地提示音 | 该轮不调用灵矽；未命中时仍需云端回退 |
| 灵矽交互 | 浏览器麦克风 → DuckKing → 灵矽 | 云端回复音频 → 浏览器播放 | 是 |
| 预录本地演示／合唱 | 剧本、预录素材或乐谱，无需真人讲话 | 浏览器播放录音或合成声部 | 本地模式不依赖；实连预录指令模式另有真实云端调用 |

当前没有“鸭 A 的声音经过虚拟空间，被鸭 B 听到并识别”的链路；多鸭合唱是程序调度和混音，也没有实现一套通用离线对话与实时 TTS。官方另有本地鸭叫、合唱以及在电脑上合成整套声部的声音工具，但 DuckKing 的 Web Audio 演出不能当作已经接入这些板载能力。[官方声音与合唱说明](https://github.com/pollen-robotics/microduck/blob/main/docs/robot/cheatsheet.md#the-voice)

后续建议独立定义音频设备层，职责为“采集 PCM、播放 PCM／本地素材、清空播放队列、报告设备状态”。浏览器和实体音频设备分别实现这组职责，灵矽与本地识别复用上层流程。**这是接口设计建议，当前没有名为 `AudioIO` 的统一实体设备实现。** 板载采集还需要验证采样率、声道、回声、播录并发和断开后的释放行为。

## 4. 需要替换的仿真信息

| 当前依据 | 实体接入的候选实现与待验证项 |
|---|---|
| MuJoCo 中球的精确坐标、脚球接触和位移 | 球的位置与距离感知、实际踢球结果观测；视觉／深度等方案尚未在本项目接入 |
| 嘴部接触垫、轻棒接触和夹持状态 | 实机嘴部行程与力度校准、夹持反馈及物体滑落判断；反馈来自哪些传感器需实际确认 |
| 鸭子的全局位置、朝向、射线遮挡 | 定位、视觉或其他感知方案，带时间戳和不确定性；不把估算坐标冒充精确真值 |
| 物理接触与姿态阈值判定“坐稳／站稳” | 官方遥测与适用的姿态传感器，重新标定阈值并检查反馈是否过期 |
| 同一个进程中的四鸭时钟与声部播放 | 每台设备独立时钟、网络或官方同步方案，以及丢包、迟到和设备离线策略 |
| 重置场景、摆球、把鸭放到初始位置 | 人工准备或另行设计实体动作；不能将仿真位姿写入包装成机器人会自主摆放 |

当前搬运嘴部是对模型的实验改编，参数没有实机标定；原样使用仿真质量、摩擦与关节参数并不能证明实体夹持可靠。桌沿跌落等演出剧情保留为仿真节目，不列为默认实机接入验收任务。

## 5. 推荐接入顺序

以下阶段均为**待实施的实体计划**，不改变现有服务器部署，也不要求重写整个项目。

| 阶段 | 工作范围 | 完成条件 |
|---|---|---|
| 1. 固定接入版本 | 记录硬件型号、固件提交、策略版本、协议和音频设备；建立独立身份与连接 | 能读到真实健康与姿态状态，断连时明确报离线，无法获得状态时不伪造成功 |
| 2. 单鸭基础闭环 | 先点头／转头，再短距离移动、停止、打断和新命令替换 | 命令、实际动作、停止反馈对应同一请求；验证重复请求、过期遥测和断线处理 |
| 3. 小鸭自己听说 | 接入实体麦克风和扬声器，复用语音协议 | 在设备上录音、回复、打断并继续说话；记录实际声音效果与播放设备状态 |
| 4. 扩展动作与感知 | 按固件支持情况逐项接入坐站、踢球、夹持与结果判定 | 每项都有能力声明、条件、真实反馈和失败处理；没有接入的能力不公布为可执行工具 |
| 5. 多鸭协作 | 每鸭独立身份和状态，建立任务目标映射与演出同步 | 指令不会发错鸭；一台掉线可停止或按明确规则降级；用真实多设备测同步偏差 |

第一阶段可采用“现有浏览器／服务器语音 → 实机侧代理 → 本机 robotd”的过渡结构，再评估把音频和部分上层逻辑迁入鸭子。Unix socket 是本机接口，YZH737 不能直接打开实体机器人上的 socket；跨机器需要额外的受控连接与协议适配。官方控制环和电机管理继续放在实机侧，上层发送有界动作意图。

服务器上的 MuJoCo 渲染、离线识别服务和全部开发依赖不必整体搬上板。逐项测量资源后决定运行位置；本地识别留在服务器时，应称“服务器离线识别”，不能宣传为“机器人端离线”。

## 6. 复用时必须核对的接口语义

- **能力声明。** 现有动作允许列表不是实机能力清单。先为实体后端定义支持项，再调整控制器对 `kind == "mujoco"` 和 `SCENE_ACTIONS` 的分支；不能靠伪装成 MuJoCo 绕过校验。
- **完成条件。** 当前基础动作按时长发送意图，结束后调用停止；`completed` 不证明实体走了指定距离。需要距离或抓取结果的任务，应以实测反馈完成或明确失败。
- **停止边界。** `RobotdBackend` 已检查遥测时效和部分姿态标志，并发送 `robot.stop`；这不等于验证了实体急停、断网后执行状态或硬件故障处理。那些需要单独实测，不能通过改 UI 文案补齐。
- **观察边界。** 保留观测来源、时间和不可用状态。当前 robotd 适配没有编造世界坐标，实体反馈也应遵守同一原则。
- **身份与多鸭。** 身份私有持久化，房间只是公开演示空间；未来的实体设备归属、授权控制与多用户访问需要独立设计，不能将房间号当作设备授权。
- **音频与指标。** 音频到达不等于出声，命令受理不等于动作开始；浏览器、服务端与实体端时钟不同，跨端时延需要另行定义测量方法。

可复用的回归入口包括 [robotd 协议测试](../tests/test_robotd.py)、[动作边界测试](../tests/test_motion_edges.py)、[语音打断](../tests/test_voice_interrupt.py)、[故障恢复](../tests/test_voice_recovery.py)和[工坊失败处理](../tests/test_studio_failures.py)。这些测试证明现有软件契约，不能替代实机试验。

每项实机试验至少记录：硬件／固件／软件版本、输入方式、环境与动作参数、命令受理、实际结果、停止与失败情况、证据位置。先用单一动作建立可重复结果，再扩大组合和持续运行时间。

## 7. 对商业价值的补充

这条路径使 DuckKing 同时服务两个阶段：**购买前降低理解与试用成本；开始开发后提供可以接着使用的交互软件和验证入口。** 当前能交付的是代码结构、协议适配、可复现演示和测试。迁移是否节省工时、降低联调成本、提高硬件或灵矽接入意愿，需要实体接入与开发者试用验证。

后续可记录从取得硬件到首条真实语音动作的耗时、实际复用与修改的模块、每项能力联调失败的原因，以及演示用户是否继续尝试开发。不从代码行数直接推算节省比例，也不据此承诺整套演示可直接移植。
